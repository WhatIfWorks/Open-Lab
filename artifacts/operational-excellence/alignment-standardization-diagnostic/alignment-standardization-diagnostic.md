## Using This Companion

Use this guidance with teams, sites, or process owners examining whether local methods must match. Start with outcomes and non-negotiable requirements, investigate actual variation and its consequences, then test whether standardization solves a problem that alignment alone would not.

Expected outputs are observations/evidence about variation and local value, a reasoned choice among alignment, standardization, and legitimate variation, and an operating boundary describing what must be common, what must be identical, what may vary, and how it remains governed. The decision frame supports reasoning rather than scoring consistency.

::: purpose
Determine where consistency is necessary, where alignment is sufficient, and where local variation can legitimately remain.

### What It Is

A structured way to distinguish shared outcomes, requirements, interfaces, and evidence from methods that may not need to be identical.

### What It Is Not

An argument against standards, a mandate for local autonomy, or a scoring system for process consistency.

## A. Establish What Must Align

> Start with what the system must achieve and what must hold across boundaries before deciding how much of the method needs to be the same.

::: workspace blue
**What must be true when the work is complete?**

Define the result before discussing how everyone should perform the work.
:::

::: workspace cream
**Where does variation create meaningful risk, confusion, incompatibility, ambiguity, or failure?**

Identify the boundary that needs alignment without assuming the underlying methods must be identical.

### 01 Outcome

**What must be true when the work is complete?**

Define the result the system must reliably produce before prescribing the method.
:::

::: lens blue
### 02 Requirement

**What is genuinely non-negotiable?**

Consider legal, regulatory, quality, safety, customer, technical, contractual, and organizational requirements.
:::

::: lens gold
### 03 Interface

**Where must different parts of the system connect?**

Consider inputs, outputs, handoffs, data, terminology, timing, ownership, escalation, and acceptance criteria.
:::

::: lens gold
### 04 Evidence

**What must demonstrate that the requirement was met?**

Identify evidence that must be comparable, reliable, retrievable, or interpretable across the system.
:::

:::

::: lenses

::: lens blue
### 05 Variation

**What is different today?**

Describe the actual variation without assuming that the difference itself is a problem.
:::

::: lens blue
### 06 Consequence

**What happens because it is different?**

Look for measurable risk, failure, rework, incompatibility, ambiguity, cost, delay—or no meaningful consequence.
:::

::: lens gold
### 07 Local Value

**What does the variation enable?**

Consider technology, workflow, capability, regulation, customer, scale, geography, and local operating conditions.
:::

::: lens gold
### 08 Standardization

**What specifically becomes better by making this the same?**

Name the problem standardization would solve rather than treating consistency itself as the outcome.

## B. Test the Need for Standardization

> Variation is not automatically a defect. Establish what differs, what consequence that difference creates, and what value the variation may preserve.

::: eyebrow
Decision Frame
:::

::: decision
### Does Variation Create a Real Problem?

Establish the consequence before prescribing sameness.

### Yes

The variation creates a meaningful problem.

### Question

Does the method itself need to match?

### No

Preserve the local method unless another requirement demands change.

### Standardize

Make the method consistent where the method itself is necessary.

### Align

Align the requirement, interface, evidence, or outcome while allowing the method to vary.

### Allow Variation

Keep legitimate local variation where it creates value or carries no meaningful risk.
:::

::: open-lab-note
Consistency has value when variation creates a meaningful problem. But consistency is not automatically evidence of control. A system can align around outcomes, requirements, interfaces, and evidence while allowing local methods to differ where that variation creates value or carries no meaningful risk.
